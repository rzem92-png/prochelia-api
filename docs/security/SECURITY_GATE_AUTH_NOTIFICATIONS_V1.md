# PROCHÉLIA — Security gate Auth + Notifications V1

**Status:** audit / implementation gate, not a production approval.  
**Branch:** `feature/multichannel-notifications-v1`  
**No production deployment, D1 migration, real provider call, or merge is authorized by this document.**

## Scope

This gate covers account authentication, session lifecycle, transactional notifications, mission check-in codes, webhook delivery, and privacy controls. It complements (does not replace) a threat model, code review, D1 schema review, and preproduction integration tests.

## Findings requiring code-level remediation or verification

### 1. Mission security code generation
The currently inspected backend uses a 32-bit random integer modulo 1,000,000 to generate six-digit codes. Modulo reduction creates bias and 32-bit entropy is not ideal for this use. Use rejection sampling with a cryptographically secure random source, or use a sufficiently long random token where usability permits. Six-digit codes remain low entropy: enforce strict online attempt limits, per-mission and per-actor throttles, short expiry, one-time use, and lockout. Never rely on code entropy alone.

### 2. Mission webhook signature
The inspected sender computes a SHA-256 digest over `secret + "." + body`. This is **not HMAC** and must not be treated as a standard authenticated signature. Replace with HMAC-SHA-256 over the exact raw request bytes. Receiver requirements:
- verify signature using constant-time comparison;
- include timestamp and reject stale requests;
- include a unique event ID and persist replay protection;
- parse JSON only after signature verification;
- enforce HTTPS, host allowlisting and strict timeout;
- do not log request body, secret, codes, or signature.
A hash-based signature does not prove authenticity unless a proper keyed MAC is used.

### 3. Webhook URL and SSRF
If a webhook URL can be configured in runtime environment, restrict it to an approved HTTPS endpoint/domain. Do not allow user-controlled URLs, redirects to arbitrary hosts, localhost, private IP ranges, or Cloudflare metadata endpoints. Fail closed when configuration is absent or invalid.

### 4. Code delivery failure and consistency
Mission code records are created before delivery and deleted on provider failure in the inspected flow. Validate concurrency and crash behavior. Prefer a transaction/state machine such as `pending_delivery → delivered → active`, with codes unusable until delivery is confirmed. Make delivery idempotent. Never delete audit evidence; retain only safe failure metadata.

### 5. Auth/session review
Existing login uses PBKDF2-SHA-256 (100,000 iterations in inspected code) and hashed session tokens. Before production:
- benchmark password hashing under Worker CPU limits and assess current iteration policy;
- enforce login throttling and generic errors;
- ensure cookie policy matches the actual frontend/backend origin topology;
- verify CSRF defenses for cookie-authenticated state-changing requests (SameSite=None requires particular care);
- revoke all sessions on password reset / credential compromise;
- reject inactive/suspended users on every authenticated request;
- ensure session deletion and expiry behavior are covered by tests.

### 6. OTP/account recovery
OTP must be generated by CSPRNG, bound to user + purpose + challenge, stored as HMAC/hash (not plaintext), short-lived, one-time, and invalidated after success or resend. Use attempt counters and cooldowns. Use generic responses to prevent account enumeration. Apply rate limits by IP, account identifier, device/session and endpoint. Do not include OTP in logs, analytics, traces, or error responses. Avoid exposing whether an email/phone exists.

### 7. WhatsApp consent and templates
Separate transactional opt-in from marketing consent. Store consent version, timestamp, source and withdrawal. Verify phone ownership before sending account-sensitive messages. Respect opt-out and Meta template/window policies. WhatsApp must not become an automatic fallback for account recovery unless user explicitly chose and verified it. Do not put health details, sensitive service details, OTPs, or reset links in previews or ordinary notification logs.

### 8. Provider resilience
- Idempotency key per logical notification/event.
- Bounded retry with exponential backoff + jitter; retry only transient failures.
- Dead-letter/manual review for exhausted attempts.
- No infinite retries and no provider failover that changes channel without explicit consent.
- Sanitize provider responses before logging.
- Protect against duplicate events and concurrent delivery.

### 9. Data minimization / RGPD
- Keep notification logs metadata-only: provider, template, status, timestamps, hashed recipient reference, correlation ID.
- Define retention and deletion/anonymization rules before live operation.
- Restrict access to identity documents, audit trails, phone numbers and emails by role.
- Document processor contracts, transfer locations, purpose, lawful basis, opt-in evidence and data-subject request handling.
- Avoid placing identity documents or sensitive details in WhatsApp/email.

## Required tests before approval

### Authentication/session
- login success/failure/inactive account;
- login rate limit and generic response;
- session expiry, logout, revocation and cookie flags;
- CSRF rejection for cookie-authenticated writes;
- password reset invalidates prior sessions;
- role escalation / IDOR attempts denied.

### OTP
- valid, invalid, expired, reused, wrong-purpose, wrong-user;
- concurrent redemption permits exactly one success;
- resend invalidates previous challenge;
- max attempts / cooldown / rate limits;
- account enumeration parity;
- no OTP leakage in logs/errors.

### Mission security
- code generation distribution and invalid input;
- expired/used/wrong-purpose code rejected;
- lockout and concurrent verification;
- verified identity requirement;
- mission/client/intervenant relationship checks;
- state transitions and delivery failure/crash recovery;
- audit log contains no plaintext codes.

### Webhook
- valid HMAC accepted;
- invalid/missing signature rejected;
- stale timestamp rejected;
- replay/event duplicate rejected;
- body tampering rejected;
- timeout, redirect, DNS/host restrictions;
- secret rotation and no secret leakage.

### Notifications
- WhatsApp opt-in absent/withdrawn -> no send;
- approved template required when applicable;
- Resend/Meta errors normalized and redacted;
- idempotency and duplicate events;
- bounded retries and provider outage;
- no real provider calls in CI.

## Release gate

Do not merge or deploy until:
1. code changes and review are complete;
2. automated unit/security tests pass;
3. integration tests pass in isolated preproduction;
4. provider secrets and sender identities are validated without exposing secrets;
5. D1 schema/backup/restore and retention plan are reviewed;
6. legal/RGPD and payment flows are approved by responsible humans;
7. rollback and incident response are documented;
8. explicit release authorization is recorded.

Passing mocked provider tests only validates adapter behavior. It does **not** validate OTP security, WhatsApp consent, webhook authenticity, D1 behavior, or production readiness.


## Addendum — review de concurrence (4 novembre 2026)

### Rate limiting D1 — BLOQUANT avant trafic réel

Le code de limitation observé dans `productionRateLimit()` fait actuellement un `SELECT request_count`, puis un `UPDATE` ou `INSERT` séparé. Cette séquence n'est pas atomique : deux requêtes simultanées peuvent lire le même compteur et écraser l'incrément de l'autre; lors du premier hit, deux `INSERT` peuvent aussi se heurter à la contrainte unique. Un attaquant peut exploiter ce comportement pour dépasser le seuil ou provoquer des erreurs 500.

**Remédiation requise :** remplacer le read-modify-write par un incrément SQL atomique (`INSERT ... ON CONFLICT ... DO UPDATE SET request_count=request_count+1`) sur une clé unique `(bucket, subject_hash, window_start)`, puis lire le compteur; vérifier le comportement D1 en test concurrentiel. Si une seule opération atomique de comptage + décision n'est pas garantie, utiliser un mécanisme durable adapté (par exemple Durable Object) pour les limites strictes. Les limites IP seules ne suffisent pas : ajouter clés par compte/acteur et route, avec limites distinctes pour OTP/login, mission-code, webhook et paiements.

**État :** constat documenté, correctif de code non intégré ici; ne pas déclarer le rate limiting robuste tant que le patch et les tests de concurrence ne sont pas passés.

### Tests à ajouter au gate

- Au moins 100 requêtes concurrentes dans la même fenêtre : aucun incrément perdu et aucun dépassement silencieux.
- Première insertion concurrente sur une clé inexistante : pas d'erreur 500, compteur final exact.
- Clé de fenêtre suivante : compteur indépendant, expiration/nettoyage sans supprimer les traces d'audit.
- Limites par IP et par compte : pas de contournement trivial via changement de route ou de casse/normalisation d'identifiant.


## Addendum — paiements, idempotence et reprise (4 novembre 2026)

### Webhook PSP — crash après réservation d'événement

L'implémentation inspectée insère l'événement dans `payment_webhook_events` avec `INSERT OR IGNORE`, puis applique les effets métier. En cas d'arrêt/crash après l'insertion et avant la fin du traitement, la livraison suivante peut être considérée comme doublon alors que les effets métier n'ont pas été appliqués. La colonne `processed` existe mais ne suffit pas à gérer cette reprise.

**Gate bloquant avant paiements réels :** adopter un état durable (`received/processing/processed/failed_retryable/failed_terminal`), horodatage/lease et nombre de tentatives; ne répondre succès au PSP qu'après traitement durable, ou fournir une reprise des événements non traités. Le handler doit être idempotent au niveau des effets (ledger/transaction), pas uniquement de l'identifiant d'événement. Détecter même event ID avec payload hash différent et le placer en anomalie/audit. Tester crash simulé avant/après chaque écriture, livraison répétée, deux workers simultanés, timeout et reprise.

### Crédit wallet — risque de double effet

Le flux aperçu crédite le wallet intervenant lors de `payment_succeeded`. Il faut une contrainte d'unicité/ledger sur l'effet de crédit (transaction/provider-event/effet) et une opération atomique conditionnelle. La seule vérification du statut de la transaction n'est pas une garantie suffisante si plusieurs webhooks concurrents lisent le même statut avant mise à jour.

**État :** risque documenté, correctif non intégré ni validé par tests d'intégration D1. Les paiements réels restent interdits.
